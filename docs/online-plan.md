# Онлайн-режим: план и ревью (ветка online/p2p, 23.11)

Цель: друг открывает ссылку и играет с хостом. Сервера нет — партия живёт в браузере хоста, связь браузеров напрямую (WebRTC). Рядом с людьми могут сидеть боты (их считает хост).

## 1. Ресёрч: как это делают другие

| Решение                                                                                                                                      | Что берём                                                                                                            | Чего избегаем                                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **boardgame.io `@boardgame.io/p2p`** — хост держит авторитетное состояние в своём браузере, остальные подключаются по `matchID` через PeerJS | Та же модель «хост-мастер», фильтр секретов на стороне мастера (`playerView`), клиенты шлют только ходы              | Пакет экспериментальный и не обновлялся с 2023; по умолчанию любой клиент может ходить за любое кресло — нужны свои «ключи кресел» |
| **PeerJS** — обёртка WebRTC с бесплатным облачным брокером сигналинга                                                                        | Простой API data-канала                                                                                              | Публичный брокер без SLA, на нём жалуются на таймауты; TURN-сервера нет совсем                                                     |
| **Trystero** — комнаты WebRTC с сигналингом через публичные сети (Nostr, MQTT, BitTorrent, Firebase), без своего сервера, данные шифруются   | Нет единственной точки отказа в виде брокера; API «комната + действия» ложится на нашу схему; поддерживает свои TURN | Зависимость от чужих публичных реле для поиска пира                                                                                |
| **TURN** (Cloudflare Realtime: 1000 ГБ/мес бесплатно; учётки до 48 ч)                                                                        | Для 10–20% сетей (мобильные, корпоративные) прямое соединение не строится без TURN                                   | Учётку Cloudflare нельзя класть в клиент — нужен крошечный бэкенд для выдачи; на старте обходимся без TURN                         |

Вывод: наша архитектура (чистое ядро, `getObservation`, `determinize`, запись `config + seed + actions`) уже совпадает с моделью boardgame.io, брать сам фреймворк не нужно.

## 2. Строгое ревью первоначального плана

Первоначальный план: (1) переписать интерфейс на наблюдение → (2) транспорт → (3) WebRTC через PeerJS → (4) лобби → (5) публикация.

| #   | Замечание                                                                                                                                                       | Тяжесть                  | Решение                                                                                                                                                                                                                            |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Этап 1 («переписать экран на наблюдение») — самый дорогой и рискованный: экран использует полное состояние в 10+ местах (предпросмотр ходов, силы, очки, окна). | Высокая                  | **Не переписывать.** Гость рисует экран из `determinize(наблюдение)` — это полное игровое состояние, где скрытое заменено догадками. Компоненты не меняются; утечь нечему, потому что настоящих скрытых данных у гостя просто нет. |
| 2   | Журнал и окна (итоги боя, тосты) строятся из **событий** ядра, а события могут нести скрытое (например, будущие события колоды). В плане это не учтено.         | Высокая                  | Хост шлёт гостю не события, а только наблюдение + отфильтрованные события: в ядре — функция `eventsFor(events, viewer)`, с тестом «никакое событие не раскрывает чужое скрытое».                                                   |
| 3   | Не было защиты кресел: любой подключившийся мог бы ходить за любого.                                                                                            | Высокая                  | Ключ кресла (случайный токен) в ссылке-приглашении и в localStorage гостя; хост принимает ход, только если токен совпал и ход есть в `getLegalActions` для этого кресла.                                                           |
| 4   | PeerJS как единственный транспорт: брокер без SLA.                                                                                                              | Средняя                  | Транспорт — интерфейс. Реализации: в памяти (тесты), BroadcastChannel (два окна одного браузера, отладка), WebRTC. Выбор PeerJS vs Trystero — короткий спайк на этапе 3, по результату реального подключения с двух сетей.         |
| 5   | Не продуман рассинхрон: потеря сообщения, повторный ход, переподключение.                                                                                       | Средняя                  | Каждое сообщение хоста — полный снимок (наблюдение + номер версии `seq`), а не дифф. Гость шлёт ход с `seq`, на котором он его выбрал; устаревший ход хост отклоняет и шлёт свежий снимок. Снимки маленькие (JSON партии ~5 КБ).   |
| 6   | Разные версии кода у хоста и гостя (кэш, обновление сайта).                                                                                                     | Средняя                  | В рукопожатии — версия сборки и хеш правил; при расхождении гость видит «обновите страницу».                                                                                                                                       |
| 7   | Хост закрыл вкладку — партия пропала.                                                                                                                           | Средняя                  | Уже есть сохранение в localStorage; хост открывает страницу снова — комната поднимается с той же ссылкой. Перенос роли хоста — вне рамок.                                                                                          |
| 8   | Отмена хода и «Ход назад» в онлайне ломают честность.                                                                                                           | Низкая                   | В онлайне отключены; «Ход назад» на экране ошибки — только у хоста.                                                                                                                                                                |
| 9   | Без TURN часть пар не соединится.                                                                                                                               | Низкая для игры с другом | На старте — только STUN; если у друга не соединяется, добавим TURN (Cloudflare + функция выдачи учёток).                                                                                                                           |
| 10  | Где жить коду: новый пакет или `web`.                                                                                                                           | Низкая                   | `packages/web/src/online/` (протокол, сессия хоста/гостя, транспорты). Ядро получает только `eventsFor`. Новый пакет не нужен, границы `data ← core ← bots ← web` не меняются.                                                     |

## 3. Итоговый план по этапам

Каждый этап: код → `npm run check` → прогон интерфейса (uiStress) → **код-ревью (агент reviewer) и ревью архитектуры** → остановка на проверку автором.

1. **Вид гостя без утечек.**
   - Ядро: `eventsFor(events, viewer)` + тест, что события для зрителя не раскрывают скрытое.
   - Экран партии получает «источник вида»: локальный (полное состояние, как сейчас) или удалённый (`determinize(наблюдение)` + отфильтрованные события + список ходов от хоста).
   - uiStress: дополнительно рисует экран глазами каждого игрока из `determinize` и проверяет, что в разметке нет скрытого (чужие жетоны до вскрытия, порядок колоды).
2. **Протокол и сессия на транспорте в памяти.**
   - Сообщения: `hello {seatToken, build}` → `snapshot {seq, observation, legal, events}`; `act {seq, action}` → `snapshot` или `reject {reason}`.
   - Хост: кресла, ключи, проверка ходов, ходы ботов, рассылка снимков. Гость: приём снимков, отправка ходов.
   - Тесты: две сессии на транспорте в памяти доигрывают партию; чужой ключ и устаревший `seq` отклоняются.
   - Транспорт BroadcastChannel: два окна одного браузера играют друг с другом.
3. **WebRTC.** Спайк PeerJS и Trystero (подключение с двух разных сетей, переподключение), выбор, реализация транспорта. Ссылка-приглашение `?room=…&seat=…&key=…`.
4. **Лобби и переподключение.** Хост выбирает кресла (я / бот / гость), копирует ссылки; гость видит «ожидание хоста»; восстановление после обновления страницы с обеих сторон.
5. **Публикация.** Статическая сборка на GitHub Pages, проверка игры с двух устройств.

## 4. Этап 1 — итоги (23.11)

Сделано:

- `packages/core/src/visibility.ts` — `eventsFor(events, viewer)`: исчерпывающая таблица видимости событий (новый тип события не скомпилируется без решения). Сейчас все события открыты.
- `screenView(..., remote)` — экран гостя: фиксированное кресло, ходы от хоста.
- `packages/web/src/screenCheck.tsx` — общая отрисовка экрана для тестов и `checkGuestView`: экран игрока из настоящего состояния и экран гостя из `determinize` его наблюдения должны совпасть.
- Тесты: `visibility.test.ts` (фильтр событий на искусственной таблице, `getObservation(determinize(obs)) = obs` на каждом ходу, снимок для сети без колоды, генератора и чужих жетонов до вскрытия); `guestView.test.tsx` в `npm test` (2 партии, каждый 4-й ход, 3 зрителя × 2 догадки); полный вариант — в `uiStress.test.tsx`.

Решения по итогам ревью (агент reviewer + ревью архитектуры):

- Журнал, тосты, подсветка последнего хода и окно итогов боя у гостя строятся **только** из событий, прошедших `eventsFor` на стороне хоста (этап 2: хост шлёт их в снимке).
- Гость получает снимок как сериализованную копию (JSON), даже на транспорте в памяти: иначе тест не докажет, что снимок переживает сеть.
- Состояние гостя (`determinize`) нельзя продвигать дальше следующего решения: предпросмотр ходов обрезается на `STOP`/`HIDDEN` в ActionBar.tsx и не должен проходить через случайность.

Отложено: два входа `screenView`/`remoteView` и переименование `botTurn`; проверка 2 и 4 игроков; проверка тай-брейков `compareForRank` на скрытое; гостевой экран с выбранным рабочим и раскрытыми вариантами.

## 5. Этап 2 — итоги (23.11)

Сделано (`packages/web/src/online/`):

- `protocol.ts` — сообщения: гость `hello` / `act` / `ping`, хост `snapshot` / `reject` / `pong`; разбор недоверенных сообщений (форма, целые числа, длина ключа); канонический `sameAction` (порядок полей не важен).
- `transport.ts` — `Link` / `Listener`, `memoryNetwork` (сообщения через JSON, как по сети); `broadcast.ts` — вкладки одного браузера.
- `host.ts` — ключи кресел; ход принимается, только если совпал `seq`, очередь кресла и ход есть среди допустимых, причём применяется ход из списка, а не объект из сети; отказ `failed`, если ход не применился; одно кресло на соединение; проверка связи: тишина дольше `LINK_TIMEOUT_MS` — соединение закрывается; нумерация снимков продолжается с версии партии (`initialSeq`).
- `guest.ts` — повтор `hello` до первого снимка, проверка связи, закрытие связи при молчании хоста.
- `connect.ts` — связь со store: хост рассылает снимки по версии store, комнату держит одна вкладка браузера (Web Locks), гость переподключается сам, `pagehide` закрывает соединения.
- store: `version`/`lastEvents`, `hostRoom`, `guest`, `sendAction`, `loadSnapshot`; отмена хода выключена онлайн; страница гостя не читает и не трогает сохранение партии этого браузера.
- Интерфейс: кресло «Гость по ссылке», ссылки-приглашения и «в сети / не в сети» у хоста, статус и экран ожидания у гостя.
- Тесты: 13 тестов протокола (партия целиком, все отказы, порядок полей, таймауты хоста и гостя, `initialSeq`, разбор битых сообщений, скрытое в снимках), 2 теста BroadcastChannel (включая «гость открыл ссылку раньше хоста»).
- Проверено в браузере: хост и гость в двух вкладках, ход гостя доходит до хоста; перезагрузка вкладки хоста — гость переподключается за ~1 с.

Ревью (агент reviewer): блокирующих по безопасности нет; три блокирующих по корректности (нумерация после перезагрузки хоста, переподключение гостя, обнаружение обрыва) исправлены вместе с большей частью желательных.

Отложено: тест связки store ↔ сессии (store один на процесс — нужен отдельный стор на сторону); хвост журнала гостю при переподключении (сейчас журнал гостя начинается с момента подключения); очистка подписок при горячей перезагрузке Vite; сужение типа `Seat`.

## 6. Этап 3 — итоги (23.11)

- Транспорт WebRTC на Trystero 0.26.0 (`online/webrtc.ts`): поиск пира через публичные реле Nostr, пароль комнаты шифрует сигналинг, данные — напрямую по DTLS. Отдельного спайка PeerJS не было: выбран Trystero по ресёрчу (нет единого брокера, живые релизы).
- У каждого гостя своя комната `ключ партии-ключ кресла`: другой гость не может выдать себя за хоста.
- Ссылка-приглашение: `#join=<ключ партии>&key=<ключ кресла>[&net=tabs]` — ключи во фрагменте, на сервер не уходят; `<meta name="referrer" content="no-referrer">`.
- Предел входящего сообщения 1 МБ; Trystero грузится лениво, только в онлайн-партии.
- Гость через 15 с без ответа видит подсказку: хост не открыл партию или сети не пропускают прямое соединение.
- **Ограничение:** TURN-сервера нет — примерно у каждой 10-й пары сетей (мобильный интернет, корпоративные сети) соединение не построится. Решение при необходимости: Cloudflare TURN + маленькая функция выдачи учёток.
- Проверено: две вкладки одного компьютера через настоящие реле (подключение ~1 с, ход ~110 мс). **Не проверено между разными сетями** — нужна проверка автором с другом: дом ↔ мобильный интернет, разные Wi-Fi, перезагрузка хоста, сон ноутбука.
- Отложено: кадр `bye` от хоста забытому гостю, тесты обёртки настоящего Trystero.

## 7. Связь через сервер `npm run online` (23.11)

Проверка с другом показала: WebRTC через публичные реле Nostr между разными устройствами не соединился ни в одном Wi-Fi, ни с мобильного (из пяти реле у гостя работали два, одно отклоняло события как «просроченные» — чувствительно к часам). Поэтому для `npm run online` связь идёт через свой сервер:

- `online/relayHub.ts` — ретранслятор (чистая логика): хост и гости подключаются WebSocket'ом к `/relay` того же адреса, что и страница; комнаты — те же `ключ партии-ключ кресла`; ретранслятор пересылает сообщения, ничего не храня.
- `scripts/online.mjs` подключает его к серверу `vite preview` (библиотека `ws` 8.22.1, только для скрипта) и собирает игру с `VITE_ONLINE_NET=relay`.
- `online/relay.ts` — транспорт в браузере (хост переподключается к ретранслятору сам).
- Способ связи: сборка `npm run online` — ретранслятор; обычная сборка и dev — WebRTC; `net=tabs|relay|webrtc` в адресе переопределяет.
- Проверено через настоящий туннель: подключение гостя 0,3 с, ход туда-обратно 66 мс. Между разными устройствами — проверить автором.
- Минусы: работает, пока запущен `npm run online`; данные идут через Cloudflare (до туннеля зашифрованы, но не сквозь); адрес новый при каждом запуске.
