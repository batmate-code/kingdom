# Вампирская игра — правила работы

Цифровая версия настольной игры: движок правил, боты, симулятор партий и браузерный интерфейс. Бриф проекта лежит в docs/brief.md.

## Источники правил

Правила — единственный источник истины, код их не додумывает. Приоритет по убыванию:

1. docs/author-answers-*.md — свежие ответы автора, перекрывают всё ниже.
2. Раздел «Уточнения из голосового разбора» в docs/rules.md.
3. Остальной docs/rules.md.
4. Изображения компонентов в docs/images/ (поле, локации, здания, жетоны, легенда, планшет).

Если правило неясно или противоречиво:

- его не угадывают: вопрос записывается в docs/open-questions.md (с номером, ссылкой на пункт правил и вариантами);
- в коде оно становится переключателем в `GameConfig` с выбранным значением по умолчанию и комментарием `// OQ-<номер>`.

## Пакеты и границы

npm workspaces, пакеты в packages/. Зависимости идут только сверху вниз: data ← core ← bots ← sim/web. Это проверяет ESLint (`no-restricted-imports`).

| Пакет         | Назначение                                    | Может зависеть от |
| ------------- | --------------------------------------------- | ----------------- |
| @vampire/data | Таблицы правил как чистые данные (без логики) | —                 |
| @vampire/core | Чистый движок правил                          | data              |
| @vampire/bots | Боты: случайный, эвристический, ISMCTS        | core              |
| @vampire/sim  | Консольный симулятор, CSV/JSON                | core, bots        |
| @vampire/web  | Vite + React + Zustand, CSS-модули            | core, bots        |

Пакеты экспортируют исходники TypeScript (`exports: ./src/index.ts`), отдельной сборки библиотек нет. Импорт между пакетами — только через `@vampire/*`, без относительных путей.

## Устройство ядра

- **API:** `createGame(config, seed)`, `getLegalActions(state)`, `applyAction(state, action)` → `{ state, events }`, `getObservation(state, player)`, `isTerminal(state)`, `getScores(state)`.
- **Конечный автомат:** в состоянии всегда есть `pending` — кто сейчас выбирает и какой выбор. Каждый выбор игрока — действие; человек и бот пользуются одним API.
- **Эффекты** (персонажи, здания, локации) — обработчики, зарегистрированные по id из data. Незавершённая цепочка эффектов хранится в состоянии как очередь сериализуемых записей `{ effectId, params }`, без замыканий и классов.
- **Состояние** неизменяемо (Immer) и сериализуется в JSON без потерь. Запись партии — `config + seed + actions[]`.
- **Случайность** только через seed-генератор, его состояние лежит внутри состояния игры. `Math.random` и `Date.now` в data/core/bots запрещены линтером.
- **Скрытая информация** (жетоны боя до вскрытия, порядок колоды, состояние генератора) видна только через `getObservation`. Для ISMCTS — `determinize(observation, rng)`.
- **Инварианты** проверяются после каждого действия в режиме разработки: ресурсы ≥ 0, треки в пределах максимума, не больше 3 зданий одного типа у игрока, одна Цитадель на регион, число рабочих постоянно.
- **Число игроков** 2–4 задаётся в config, параметры игры для всех одинаковые (как для троих).

## Стиль кода

- TypeScript strict, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`.
- Идентификаторы на английском. Комментарии, тексты интерфейса, документы и названия тестов — на русском.
- Id игровых сущностей — строковые литералы на английском (`crypt`, `abbey`, `spy`, `forest`); русские названия живут в data.
- Без `any` и `as` без необходимости; union-типы с дискриминантом `type`.

## Тесты

- Vitest. Тест лежит рядом с модулем: `foo.ts` → `foo.test.ts`.
- Тесты-сценарии по правилам: `*.rules.test.ts`, в названии ссылка на пункт правил.
- Каждая новая механика, персонаж или здание — со своим тестом.

## Команды

- `npm run check` — typecheck, lint, проверка форматирования и тесты (должно проходить перед коммитом).
- `npm test`, `npm run test:watch` — только тесты.
- `npm run dev` — веб-интерфейс.
- `npm run sim -- <аргументы>` — симулятор.
- `npm run format` — Prettier.

## Процесс

- Работаем по этапам из docs/brief.md. После каждого этапа — остановка для проверки автором.
- Этап готов, когда `npm run check` проходит, reviewer и rules-auditor не нашли блокирующих замечаний, а docs/progress.md обновлён (что сделано, что осталось).
- Агенты лежат в .claude/agents/: implementer, reviewer, rules-auditor. Одновременно работают не больше двух агентов; для кода и ревью хватает Sonnet.
- Коммиты делаются только по просьбе автора, по одному на этап или логическую часть.
